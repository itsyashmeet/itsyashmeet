<a name="trioos"></a>
<div align="center">
<h1>TrioOS</h1>

AI-powered ERP for digital marketing agencies — clients, employees, campaigns, and marketplace operations in one workspace.

<code>Next.js</code> <code>TypeScript</code> <code>Supabase</code> &nbsp; <img src="https://img.shields.io/badge/PRIVATE-8B5CF6?style=flat-square" valign="middle"/>

<br/><br/>

<img src="trioos-ceo-dashboard.png" width="92%"/>

</div>

<br/>

**Overview**
TrioOS is Trio India's internal business management platform — the operational backbone of the agency. It replaces a patchwork of spreadsheets and chat threads with a single workspace covering clients, employees, campaigns, and marketplace operations.

**Problem Statement**
As Trio grew across multiple marketplaces and client accounts, there was no single source of truth. Client details lived in one sheet, employee performance in another, and there was no structured way to track who was responsible for what — or how well they were performing.

**Solution**
A unified, role-aware platform with dedicated modules for clients, employees, and team leadership, built on Next.js and Supabase so the whole team works off live data instead of static exports.

**Core Features**
- Client detail pages with full account history
- Employee detail pages with a performance-scoring formula
- Team Leader role module for delegated oversight
- Client import pipeline (bulk onboarding via structured import modal)
- In-app notifications system
- Premium login experience with a split-panel, glassmorphism design
- Reusable dashboard primitives: `StatCard`, `ChartCard`, `ActivityCard`

**Tech Stack**
Next.js · TypeScript · Supabase (Postgres, Auth, Row-Level Security) · Tailwind CSS · shadcn/ui

**Architecture Overview**

```mermaid
flowchart LR
    A[Next.js App Router] --> B[Auth Middleware]
    B --> C{Role Check}
    C -->|Admin/CEO| D[Executive Dashboard]
    C -->|Team Leader| E[Team Module]
    C -->|Employee| F[Personal Workspace]
    D & E & F --> G[Supabase Client]
    G --> H[(Postgres + RLS)]
    G --> I[Realtime Notifications]
```

**Key Challenges Solved**
- Supabase foreign-key joins using `table!fkey` syntax were failing silently in production. The reliable fix was decomposing the query — fetching related rows separately and merging them manually in application code, rather than trusting the implicit join.
- A recurring "nested `DialogContent`" bug was breaking the Client Import modal; resolved by flattening the modal composition instead of nesting dialog primitives.
- TypeScript/Supabase type generation gaps required iterative, deliberate `as any` casting at well-documented boundaries rather than loosening types globally.

**Current Status**
Actively developed and in daily internal use at Trio India. Core modules (clients, employees, notifications, auth) are live; the Team Leader module and performance-scoring system are recent additions.

**Future Roadmap**
Expand campaign-tracking modules, unify the design system with Trio Billing, and move more of the reporting layer to real-time Supabase subscriptions.

<h1>Trio Billing</h1>

A production-grade GST billing SaaS for Indian businesses — invoicing, inventory, and A4-ready document generation.

<code>Next.js 16</code> <code>React 19</code> <code>shadcn/ui</code> &nbsp; <img src="https://img.shields.io/badge/PRIVATE-8B5CF6?style=flat-square" valign="middle"/>

<br/><br/>

<img src="trio-billing.png" width="92%"/>

</div>

<br/>

**Overview**
Trio Billing is a standalone SaaS for GST-compliant invoicing, customer and item management, built specifically around the layout and tax conventions Indian businesses expect on a printed A4 invoice.

**Problem Statement**
Most generic billing tools either ignore Indian GST formatting conventions or produce documents that don't map cleanly to what a business actually wants to hand a customer or file with. Small businesses were stuck between spreadsheets and expensive enterprise software.

**Solution**
A focused, modern billing app: clean auth and dashboard shell first, then Customers, Items, and Invoices built as tightly-scoped milestones — each shippable and testable on its own.

**Core Features**
- Authenticated, protected dashboard with sidebar navigation
- Milestone-based build: Auth → Dashboard Shell → Customers → Items → Invoices
- `CompanyHeader` component for tax-invoice headers — flexbox layout, right-aligned contact block, vertical divider, matched pixel-for-pixel to a reference design
- GST-correct invoice formatting built for Indian tax compliance
- A4-ready print/export layouts

**Tech Stack**
Next.js 16 · React 19 · TypeScript · Tailwind CSS · shadcn/ui · Supabase

**Architecture Overview — Billing Workflow**

```mermaid
sequenceDiagram
    participant U as User
    participant D as Dashboard
    participant S as Supabase
    participant I as Invoice Engine
    U->>D: Create Customer / Item
    D->>S: Persist record (RLS-scoped)
    U->>D: Generate Invoice
    D->>I: Compile line items + GST rules
    I->>S: Fetch customer + item data
    I-->>D: Rendered A4 invoice
    D-->>U: Print / Export / Send
```

**Key Challenges Solved**
- Replicating a pixel-precise reference invoice header using pure flexbox (right-aligned contact details, vertical separators) without hardcoding fragile absolute positioning.
- Structuring the schema so Customers, Items, and Invoices could each ship as an independent milestone without rework once the next module landed.

**Current Status**
Milestone 1 complete — auth, middleware, and the protected dashboard/sidebar layout are live. Customers, Items, and Invoices are the active build targets.

**Future Roadmap**
Full invoice lifecycle (draft → sent → paid), inventory-aware item tracking, and PDF export aligned with the same document-generation standards used across Trio's other tools.

<h1>Trio AI Listing</h1>

An AI-powered Amazon listing generator that automates product content creation and bulk listing generation at scale.

<code>OpenAI API</code> <code>Gemini API</code> <code>Automation</code> &nbsp; <img src="https://img.shields.io/badge/PRIVATE-8B5CF6?style=flat-square" valign="middle"/>

<br/><br/>

<img src="trio-ai-listing.png" width="92%"/>

<br/>

**Overview**
Trio AI Listing turns raw product details into marketplace-ready Amazon listing content — titles, bullet points, and descriptions — at bulk scale, for Trio's D2C and marketplace-seller clients.

**Problem Statement**
Writing high-converting, policy-compliant Amazon listings by hand doesn't scale once an account manager is handling dozens of SKUs across multiple client catalogs. Manual listing content is slow, inconsistent, and easy to get wrong on formatting rules.

**Solution**
A structured AI pipeline that takes product attributes as input and returns marketplace-formatted listing content as structured output — not free-form text that needs manual cleanup — with both OpenAI and Gemini as interchangeable generation backends.

**Core Features**
- Bulk listing generation across many SKUs in one pass
- Structured-output prompting so results map directly into listing fields (no manual reformatting)
- Dual-provider AI backend (OpenAI + Gemini)
- Content tuned for Amazon's listing constraints and character limits

**Tech Stack**
OpenAI API · Gemini API · Automation/scripting layer

**Architecture Overview**

```mermaid
flowchart TD
    A[Product Attribute Input] --> B[Prompt Template Builder]
    B --> C{Provider Router}
    C -->|Primary| D[OpenAI API]
    C -->|Fallback| E[Gemini API]
    D & E --> F[Structured JSON Output]
    F --> G[Validation Layer]
    G -->|Pass| H[Listing Ready for Upload]
    G -->|Fail| B
```

**Key Challenges Solved**
- Getting consistent, structured output from a generative model reliably enough to skip manual review on every single listing — solved by strict prompt templating and output validation rather than trusting free-form generation.
- Designing prompts that respect Amazon's character-limit and formatting constraints without truncating mid-sentence.

**Current Status**
In active development as an internal tool supporting bulk listing workflows for Trio's marketplace clients.

**Future Roadmap**
Add automated quality scoring for generated listings, expand beyond Amazon to Flipkart and Meesho listing formats, and add direct upload integration with marketplace seller panels.

<h1>SLA Generator</h1>

A platform-specific SLA document generator for Amazon, Flipkart, and Meesho sellers, with automated filtering and export.

<code>React</code> <code>Vite</code> <code>Vercel</code> &nbsp; <img src="https://img.shields.io/badge/LIVE-A78BFA?style=flat-square" valign="middle"/>

<br/>

<br/>

**Overview**
SLA Generator is a standalone, publicly deployed web app that produces platform-specific Service Level Agreement documents for Amazon, Flipkart, and Meesho sellers — Trio's first fully shipped and live product.

**Problem Statement**
Each marketplace has different SLA terms, and account managers were manually assembling these documents per client per platform — slow, repetitive, and error-prone.

**Solution**
A React app where a user selects the relevant platform(s), fills in per-field details with inline editing, and gets a correctly filtered, formatted document out the other end.

**Core Features**
- Platform-specific filtering for Amazon, Flipkart, and Meesho (with a fixed `anyPlatformSelected` guard to prevent invalid empty-selection states)
- Per-field inline editing, migrated from `contentEditable` to fully React-controlled `useState` fields for reliability
- Additional Charges and Payment Schedule sections
- Fast, static deployment on Vercel

**Tech Stack**
React · Vite · Vercel

**Architecture Overview**

```mermaid
flowchart LR
    A[Platform Selection] --> B{anyPlatformSelected?}
    B -->|No| A
    B -->|Yes| C[Field Editor - useState]
    C --> D[Additional Charges]
    C --> E[Payment Schedule]
    D & E --> F[Document Assembly]
    F --> G[Export / Print]
```

**Key Challenges Solved**
- Early versions used `contentEditable` for inline document editing, which caused unreliable state and cursor behavior — rebuilt around React-controlled `useState` per field for predictable, testable editing.
- A guard condition bug allowed document generation with no platform selected; fixed with an explicit `anyPlatformSelected` check before proceeding.

**Current Status**
Live and deployed — the first product in the Trio suite to ship end-to-end.

**Future Roadmap**
Expand platform coverage as Trio onboards new marketplaces, and align its document styling with the shared design language used in TrioOS and Trio Billing.

<sub>SYSTEM DESIGN</sub>
<h1>How I Architect Larger Applications</h1>
</div>

Across TrioOS, Trio Billing, and the AI Listing tool, I follow the same underlying architecture pattern: a Next.js App Router frontend, Supabase as the single source of truth for data and auth, and a clear separation between UI components, data-fetching logic, and business rules. Role-based access is enforced both at the middleware layer and again at the database layer via Row-Level Security, so no client-side check is ever the only line of defense.

```mermaid
flowchart TB
    subgraph Client
        UI[React Components]
        State[Local/Server State]
    end
    subgraph Edge
        MW[Auth Middleware]
        RB[Role-Based Routing]
    end
    subgraph Backend
        SB[(Supabase: Postgres + RLS)]
        AI[AI Provider Layer<br/>OpenAI / Gemini]
        DOC[Document Engine<br/>Invoices / SLAs]
    end
    UI --> State --> MW --> RB
    RB --> SB
    RB --> AI
    RB --> DOC
    SB -.RLS enforced.-> Backend
```

For data-heavy modules (like employee performance scoring or invoice generation), I keep the calculation logic outside of the UI layer entirely, so it can be unit-tested and reused across dashboard widgets, exports, and reports without duplication.

<sub>AI ENGINEERING</sub>
<h1>How I Build With AI</h1>
</div>

AI is a core part of Trio AI Listing and increasingly part of TrioOS, so I treat it as an engineering discipline, not a black box.

- **Prompt Engineering** — templated prompts per content type (title vs. bullets vs. description), tuned against marketplace character-limit and formatting rules.
- **Structured Outputs** — requesting JSON-shaped responses from both providers so generated content maps directly into listing fields, with no manual reformatting step.
- **Gemini Integration** — used as a generation backend for listing content, swappable behind a common interface.
- **OpenAI Integration** — primary provider for structured listing generation.
- **AI Workflow Design** — attribute input → prompt build → provider call → structured parse → validation → ready-for-upload output.
- **Marketplace Listing Generation** — bulk generation across SKUs and catalogs rather than one-at-a-time content writing.
- **AI Quality Validation** — a validation layer checks generated output against format and constraint rules before it's considered usable, rather than trusting the model output as final.
- **AI Content Optimization** — iterating prompts based on which generated listings actually needed manual correction, closing the loop between output quality and prompt design.

<h1>How I Think About Building Software</h1>
</div>

| Principle | What it means in practice |
|---|---|
| **Production-first** | Every internal tool is built expecting real client data on day one, not a demo dataset |
| **Reusable architecture** | Shared primitives (`StatCard`, `ChartCard`, `CompanyHeader`) instead of one-off components per screen |

| **AI assists, never fabricates** | Generated content passes through a validation layer before it's treated as production-ready |
| **Deterministic over heuristic** | Where a rule can be written explicitly (GST formatting, SLA terms), it is — AI is reserved for genuinely generative tasks |

<div align="center">
<sub>DEVELOPMENT WORKFLOW</sub>
<h1>How I Ship</h1>
</div>

```mermaid
flowchart LR
    A[Identify Operational Pain Point] --> B[Define Milestone Scope]
    B --> C[Schema & Data Model First]
    C --> D[Build Reusable Components]
    D --> E[Wire Business Logic]
    E --> F[Manual QA Against Real Data]
    F --> G[Deploy - Vercel]
    G --> H[Observe Real Usage]
    H -->|Feedback| B
```

I scope every product into small, independently shippable milestones (visible directly in how Trio Billing was built: Auth → Dashboard → Customers → Items → Invoices). Each milestone is tested against real client data before moving to the next, rather than building the full app speculatively and debugging at the end.
